# What is synthetic test data?

Synthetic test data is test inputs written by an LLM instead of collected
from real users. It gets you started on [[evals]] before you have traffic,
and it lets you test a rare failure on purpose. Done carelessly, it gives
you a pile of bland, near-identical questions that look nothing like what
people actually type.

## Why "give me 50 test queries" doesn't work

Say you're building a support bot and you have no users yet. The obvious
move is to ask a model for 50 support questions. What comes back is
generic and repetitive: the same few topics, phrased the same way. Your
real users won't be that tidy, and a test set with no variety can't show
you where the bot breaks.

The fix is to decide up front how the inputs should vary, and make the
model fill in that plan.

## Dimensions, tuples, then queries

**Pick dimensions.** A dimension is one way user messages differ. For the
support bot:

- Issue type: billing, technical, general
- Customer mood: frustrated, neutral, happy
- Prior context: new issue, follow-up, already resolved

Choose dimensions that point at failures you suspect. If you don't have
any hunches yet, use the product a lot yourself, or get friends to use it.

**Write 20 tuples by hand.** A tuple picks one value from each dimension:
(billing, frustrated, follow-up). Doing the first 20 yourself forces you to
think about which combinations matter.

**Let the model make more tuples.** Either generate every combination and
have a model filter out the ones that make no sense, which guarantees
coverage of the odd corners, or ask the model for tuples directly, which
gives more realistic mixes but drifts back toward the generic and skips
rare cases. The first suits dimensions where most combinations are valid.

**Turn each tuple into a message, in a separate prompt.** Keeping this
step apart from tuple generation is what stops every query sounding the
same. For a recipe app, the tuple (vegan, Italian, multi-step) becomes "I
need a dairy-free lasagna recipe that I can prep the day before."

**Run them through the whole system and read the results.** The point of
the queries is the traces they produce. About 100 varied traces is a good
first pool for [[error-analysis]].

## Generate inputs, not answers

Have the model write what users would send, not what your system should
reply. If you let the same kind of model write the expected answers, your
test set inherits that model's biases and limits, and you end up
checking your system against them.

Ground the inputs in your real data where you can. A real estate assistant
tested this way used a test database of real listings, and grounded its
queries in real agent schedules and showing rules. A query meant to test "no listings match" should really
return zero results when you run it. If it doesn't, the test isn't testing
what you think it is.

## Where it gets tricky

**It can't tell you how often things fail.** You chose the mix of inputs,
so the failure rate on synthetic data says nothing about the rate your
users will see. For that you need real traffic, which is where
[[online-evals]] come in.

**It misses what the model doesn't know.** In specialized domains the
generated inputs can lack the details and quirks of real documents and
real users. Compare your synthetic set against real data as soon as you
have some.

**Don't generate tests for bugs you can just fix.** If your prompt never
mentions dietary restrictions, fix the prompt. Writing a batch of
dietary-restriction tests first is wasted effort.

**It tends to stay.** What starts as a stopgap until real users arrive
often becomes a permanent part of the test setup, because it covers cases
real traffic rarely hits. That's fine, as long as real traces keep being
added next to it.

## What this means when you build

- Don't ask a model for "test queries" with no structure.
- Write dimensions from your failure guesses, and 20 tuples by hand.
- Generate tuples and turn them into queries in two separate prompts.
- Generate user inputs only. Never let the model write the expected answer.
- Check each query really triggers the case it's meant to test.
- Replace or top up with real traces once you have users.
